# MXFP8 赛题前置知识手册

## 1. 为什么会有这道题

大模型、科学计算和高吞吐推理的核心矛盾主要有两个：

- **内存墙**：数据搬运速度跟不上计算速度
- **功耗墙**：高精度计算和大带宽数据传输消耗太大

传统格式如 `FP32`、`FP16` 的优点是精度高、软件生态成熟，但代价也很明显：

- 数据宽度大
- 片上/片外带宽压力大
- SRAM 和寄存器占面积
- 乘法器和加法器功耗更高

因此，低精度计算成为趋势：

- 更少的存储位宽
- 更低的访存带宽
- 更高的单位面积吞吐
- 更低的单位算力功耗

---

## 2. 什么是浮点数

浮点数的思想是把一个数分成几部分表示：

```text
value = sign x mantissa x 2^exponent
```

常见部分包括：
- `sign`：符号位
- `exponent`：指数
- `mantissa/fraction`：尾数

优点：
- 动态范围大
- 适合表示非常大和非常小的数

缺点：
- 硬件开销大
- 加法和乘法逻辑比定点复杂

---

## 3. 什么是低精度浮点

低精度浮点就是把浮点位宽做小，例如：

- FP16
- BF16
- FP8
- FP6
- FP4

位宽越小：
- 存储越省
- 乘法器越小
- 数据搬运越快

但问题是：
- 可表示数更少
- 精度更差
- 更容易溢出和下溢

所以低精度设计的核心是：

**如何在更少 bit 下尽量保留有效动态范围和足够计算精度。**

---

## 4. 什么是块浮点 Block Floating Point

块浮点的核心思想是：

一组数不再各自带完整浮点指数，而是：
- 一组数共享一个缩放因子
- 每个元素只存较短的数据部分

例如一组 32 个数：

```text
Block = {scale, x0, x1, ..., x31}
```

共享 `scale` 的好处：
- 每个元素不用都带完整指数
- 节省位宽
- 节省带宽
- 节省存储

但代价是：
- 同一个 block 内所有数共享动态范围基准
- block 内分布差异太大时，会损失精度

---

## 5. 什么是 Microscaling Formats (MX)

MX 是 OCP 定义的一类块缩放低精度格式。

它的核心不是“整个张量共用一个 scale”，而是：

- 将张量切成很多小 block
- 每个 block 各自有一个 scale
- block 内元素使用低精度格式

这比传统 `per-tensor scaling` 更灵活：

- 每个 block 可以适应自己的数值范围
- 对局部动态范围的匹配更好
- 精度通常优于整张量只用一个 scale 的方法

所以 MX 可以看成是：

**低精度元素格式 + 局部共享缩放因子**

---

## 6. 这道题里的 MXFP8 是什么

本题中的 MXFP8 包含两部分：

### 6.1 scale

- 每 32 个元素共用一个 scale
- scale 格式为 `E8M0`

### 6.2 element

- block 内每个元素是 `E4M3`
- 每个元素 8 bit

所以一个 block 的信息是：

```text
1 个 scale + 32 个 E4M3 元素
```

这就是题目里一个“数据块”的最小处理单元。

---

## 7. 什么是 E4M3

`E4M3` 表示：

- `E4`：4 bit 指数
- `M3`：3 bit 尾数
- 再加 1 bit 符号

总共 `8 bit`。

它的优点：
- 位宽很小
- 比 INT8 更适合有较大动态范围的数据

它的缺点：
- 精度明显低于 FP16/BF16
- 极值和 subnormal 处理要小心

在硬件设计里，E4M3 常见要处理的问题有：
- 正常数 normal
- 非规格化数 subnormal
- 最大值/最小值
- 0
- 舍入误差

---

## 8. 什么是 E8M0

`E8M0` 表示：

- 8 bit 指数
- 0 bit 尾数

直观理解：
- 它几乎就是“只记录 2 的幂次缩放”
- 非常适合做 block 级别的 scale

优点：
- 存储代价很低
- scale 运算简单
- 适合块缩放格式

你们在实现时通常不需要把它当成普通浮点数完整处理，而是更像：

- 一个指数偏移量
- 一个共享的 block 放缩参数

---

## 9. 为什么要 block 共享 scale

如果每个元素自己带完整浮点指数：
- 精度最好
- 但硬件和存储代价高

如果整个张量只共享一个 scale：
- 硬件简单
- 但局部精度损失可能很大

block scale 是折中：
- 比 per-element 更省
- 比 per-tensor 更灵活

块大小为什么是 32？

因为块大小是一个平衡点：
- 太小：scale 开销变大
- 太大：块内数值差异太大，精度变差

本题直接固定为 `32`，所以你们的硬件要围绕这个固定粒度优化。

---

## 10. 什么是 subnormal

subnormal 是浮点数里非常接近 0 的小数值表示。

作用：
- 让浮点数在接近 0 的区域不要突然断掉
- 保持“渐进下溢”

如果没有 subnormal：
- 很小的数会直接变成 0
- 数值误差会更突兀

硬件上：
- subnormal 处理会稍微增加逻辑复杂度
- 但题目明确要求边界测试覆盖，所以不能回避

---

## 11. 什么是矩阵乘和内积

矩阵乘本质上就是大量向量内积。

例如：

```text
Y[i][j] = sum_k A[i][k] * B[k][j]
```

其中 `sum_k` 就是内积。

本题里：
- 每个 block 长度固定是 32
- 所以一个 LLMT 单元做的是长度 32 的 dot-product

也就是：

```text
sum_{t=0..31} A_block[t] * B_block[t]
```

---

## 12. 什么是 MAC

MAC = Multiply-Accumulate，乘加。

即：

```text
acc = acc + a * b
```

大模型推理和训练里，MAC 是最核心的运算。

如果一次算很多 MAC，就能形成高吞吐矩阵乘阵列。

---

## 13. 什么是 LLMT

题目里的 `LLMT` 是：

`Low Latency MAC Tree`

可以把它理解成：
- 不是串行做 32 次 MAC
- 而是把 32 个乘积并行算出来
- 再通过低延迟加法树快速规约求和

它的目标是：
- 延迟低
- 吞吐高

但代价是：
- 硬件资源多
- 时序压力大
- 功耗可能更高

所以它是这题最重要的架构权衡点之一。

---

## 14. 什么是规约树 Reduction Tree

规约树就是把很多个数逐层相加。

例如 32 个数：

- 第 1 层：32 -> 16
- 第 2 层：16 -> 8
- 第 3 层：8 -> 4
- 第 4 层：4 -> 2
- 第 5 层：2 -> 1

优点：
- 并行度高
- 适合高吞吐

缺点：
- 树越深，时序越难
- 浮点加法器很贵
- 流水线切分要谨慎

---

## 15. 什么是 FP32 累加

虽然输入是低精度，但输出要求是 `FP32`。

原因：
- 低精度输入的乘法误差已经存在
- 如果累加也用低精度，误差会迅速放大

所以常见做法是：
- 输入低精度
- 中间乘法可用适中精度
- 最终累加用更高精度

本题明确要求：
- 累加精度是 `FP32`
- 舍入方式是 `round to even`

---

## 16. 什么是 round to even

`round to even` 是最常见的一种 IEEE 风格舍入。

直觉上：
- 如果正好卡在两个可表示值中间
- 优先舍入到“最低位为偶数”的那个值

这样做的好处：
- 相比简单的“总往上进位”，统计偏差更小
- 累计误差更均衡

硬件上要注意：
- guard bit
- round bit
- sticky bit

这些位会影响最终是否进位。

---

## 17. 什么是吞吐、延迟、面积、功耗

### 吞吐 Throughput

单位时间能做多少运算。

例如：
- 每拍做 512 个 MAC
- 时钟 1GHz

则吞吐很高。

### 延迟 Latency

一笔输入从进入到输出结果出来需要多少拍。

### 面积 Area

电路综合后所占用的硬件资源。

### 功耗 Power

运行时消耗的能量速率。

一般分为：
- 动态功耗
- 漏电功耗

---

## 18. 什么是 1 TFOPS

`TFOPS` = Tera Floating-point Operations Per Second。

`1 TFOPS = 10^12 ops/s`

如果把 1 个 MAC 看成 2 次浮点操作：

```text
1 MAC = 1 multiply + 1 add = 2 ops
```

那本题阵列：

```text
32 x 16 = 512 MAC / cycle
512 x 2 = 1024 ops / cycle
1 GHz -> 1.024 x 10^12 ops / s
```

所以理论峰值正好略高于 1 TFOPS。

---

## 19. 为什么 1GHz 很难

在 28nm 下做到 1GHz，不是说代码能综合就够了。

挑战主要来自：
- 浮点解码延迟
- 乘法器延迟
- 规约树加法深度
- FP32 累加反馈路径
- 广播扇出

所以架构设计必须考虑：
- 流水线分级
- 扇出控制
- 寄存器切分
- 关键路径定位

---

## 20. 什么是时序闭合

时序闭合的意思是：

电路在目标频率下，所有路径都能在一个时钟周期内稳定传播完成。

如果目标 1GHz：

```text
时钟周期 = 1ns
```

那么关键路径从一个寄存器到下一个寄存器，必须在 1ns 内完成。

这通常是高频设计里最难的一步。

---

## 21. 什么是综合

综合就是把 RTL 代码转成门级网表，并估计：

- 面积
- 时序
- 功耗

你们在报告里不能只写“理论上很快”，而要给出：
- 约束
- 频率目标
- 综合工具结果

---

## 22. 什么是功耗评估

功耗通常不能只看静态数字，最好结合真实切换活动。

推荐流程：
- 让阵列在接近峰值负载下跑仿真
- 导出波形或切换信息
- 用综合/功耗工具做 activity-based power estimation

这样得到的功耗结果更有说服力。

---

## 23. 为什么要做 golden model

golden model 是软件参考模型。

作用：
- 定义“正确答案”
- 验证 RTL 输出
- 做误差统计

没有 golden model，后面大规模验证和误差分析都会很痛苦。

这题几乎一定需要 Python 或 C++ 参考模型。

---

## 24. 什么是相对误差

相对误差通常定义为：

```text
relative_error = |y_hw - y_ref| / |y_ref|
```

它反映的是“相对参考值偏了多少比例”。

优点：
- 对大数和小数都比较公平

注意：
- 当 `y_ref` 非常接近 0 时，要定义好特殊处理方法

---

## 25. 这道题最重要的权衡是什么

核心权衡可以总结成三组：

### 25.1 精度 vs 面积

中间精度越高：
- 误差越小
- 面积和功耗越大

### 25.2 并行度 vs 时序

并行度越高：
- 吞吐越高
- 时序和布线越难

### 25.3 功耗 vs 频率

频率越高：
- 更容易达到目标吞吐
- 动态功耗更高
- 时序压力更大

---

## 26. 读题时最容易误解的点

### 误解 1

“只要做一个普通 FP8 MAC 阵列就行。”

不对。重点是 `MX`，也就是 block scale。

### 误解 2

“32x16 是二维普通 systolic array。”

不完全对。更接近“长度 32 的 16 路并行 dot-product engine”。

### 误解 3

“初赛只看功能。”

不对。评分表明确看：
- 方案
- 验证
- 综合
- 分析

### 误解 4

“误差给一个最大值就够了。”

不够。最好给更多统计和测试分类。

---

## 27. 建议你们团队先掌握哪些知识

开始做之前，建议至少统一这几部分：

- 浮点基础
- E4M3 / E8M0 表示法
- 块浮点和 scale 共享
- MAC / dot-product / GEMM 基础
- 浮点舍入
- 规约树和流水线
- 吞吐/频率/面积/功耗的关系
- RTL 验证基本方法

---

## 28. 给新同学的最短理解路径

如果团队里有人刚接触这个题，建议按这个顺序学：

1. 先理解矩阵乘和内积
2. 再理解浮点数
3. 再理解 E4M3 和 E8M0
4. 再理解 MX 的 block scale
5. 再理解 LLMT 和规约树
6. 最后看阵列级数据流

---

## 29. 做题时应该一直问自己的问题

每设计一个模块，都建议问：

- 这个模块处理的是数值问题还是结构问题？
- 有没有严格符合 OCP 规范？
- 中间精度是否足够？
- 关键路径在哪？
- 这部分对面积和功耗的影响大不大？
- 有没有更适合 1GHz 的流水切分？

---

## 30. 总结

这道题的本质是：

**在正确实现 MXFP8 块浮点计算规则的前提下，设计一个高吞吐、可综合、可验证、可优化的专用矩阵乘阵列。**

它同时考察：
- 数值格式理解
- 体系结构设计
- RTL 实现能力
- 验证能力
- 面积/功耗分析能力

如果你们把这五部分都做扎实，这题就不是“写一个模块”，而是一套完整的小型芯片项目。
