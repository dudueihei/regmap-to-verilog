# MXFP8 赛题拆解与执行建议

## 1. 赛题一句话总结

设计一个支持 `MXFP8` 输入格式的专用矩阵乘计算阵列，阵列等效规模为 `32 x 16`，完成：

```text
Y = A * B
```

其中：
- `A`、`B`：MXFP8 格式
- `Y`：FP32 格式

不仅要功能正确，还要满足：
- 峰值算力不低于 `1 TFOPS`
- 时钟频率不低于 `1 GHz`
- 面积和功耗尽可能低

---

## 2. 这道题到底要做什么

这题可以分成四层目标：

### 2.1 数值格式层

你们要正确实现 OCP MX 规范下的 `MXFP8` 计算规则，而不是自己定义一套近似规则。

核心点：
- 数据按 `32` 个元素分块
- 每块共享一个 `scale`
- `scale` 是 `E8M0`
- 元素是 `E4M3`
- block 乘法和累加方式要符合 OCP 规范 6.1

### 2.2 算法算子层

你们要实现的不是完整软件框架，而是一个硬件算子：

- 输入两个长度为 `32` 的 block
- 对 block 内 `32` 对元素做乘法
- 做向量内积
- 把结果累计到 FP32

### 2.3 架构实现层

题目明确要求采用类似论文参考结构：

- 一个 `LLMT` 单元完成一次长度 `32` 的 block 内积
- `16` 个 LLMT 并行工作
- 同一输入 block 广播给 16 个 LLMT
- 每个 LLMT 使用不同权重 block

### 2.4 工程交付层

除了 RTL，还要给出：
- 验证方案
- 精度结果
- 综合结果
- 功耗估算方法
- 后续优化思路

---

## 3. 推荐的需求翻译

建议你们把赛题翻译成下面这组更可执行的工程需求。

### 3.1 功能需求

必须做到：
- 支持 MXFP8 输入 block
- 支持 block 长度固定为 `32`
- 支持 16 路并行权重输入
- 支持 FP32 累加
- 支持 round-to-even

### 3.2 性能需求

必须证明：
- 目标频率 `>= 1 GHz`
- 峰值吞吐 `>= 1 TFOPS`

建议在报告里明确写出吞吐计算公式。

### 3.3 验证需求

至少需要：
- 单模块功能验证
- 端到端矩阵乘验证
- 4096x4096 规模验证
- 边界输入验证
- 随机误差验证

### 3.4 物理实现需求

至少需要：
- 28nm 假设下的综合结果
- 面积报告
- 功耗报告
- 时序报告

## 4. 如何理解 32x16 阵列

不要把它误解成传统二维 systolic array。

这题更准确的理解是：

- `32`：每个 LLMT 内部一次处理 32 个 E4M3 元素
- `16`：阵列并行输出 16 路

所以本质是：
- 内积维度 `K = 32`
- 输出并行度 `N = 16`
- 输入激活 block 广播
- 权重 block 按列并行供给

如果每个 LLMT 每拍完成一个长度 32 的点积，那么：

- 每拍 MAC 数 = `32 x 16 = 512`
- 若 1 个 MAC 计 2 ops，则：

```text
峰值吞吐 = 512 x 2 x 1 GHz = 1.024 TOPS
```

这也是题目为什么把尺寸定成 `32 x 16` 的关键原因。

## 5. 你们要交付的核心模块

建议把设计拆成下面这些模块。

### 5.1 数值解码模块

职责：
- 解码 `E4M3`
- 解码 `E8M0`
- 组合出 block 内有效数值语义

可继续拆分为：
- `e4m3_decode`
- `e8m0_decode`
- `mx_block_scale_apply`

### 5.2 Block 乘法模块

职责：
- 对 32 对元素并行乘法
- 处理 scale 对结果的影响

关键问题：
- 先乘 element 再统一处理 scale
- 还是先扩展成内部格式后乘法

### 5.3 规约树模块

职责：
- 对 32 路乘积求和

关键问题：
- 采用浮点加法树还是中间转定点/扩展格式
- 几级流水
- 面积与时序平衡

### 5.4 FP32 累加模块

职责：
- 将当前 block 点积结果累加到 FP32
- 满足 round-to-even

关键问题：
- 累加路径延迟
- 累加器反馈路径时序

### 5.5 LLMT 顶层模块

职责：
- 封装一个长度 32 的 block dot-product engine

### 5.6 16 路阵列模块

职责：
- 广播输入 block
- 分发 16 路权重 block
- 汇总 16 路输出

### 5.7 控制与接口模块

职责：
- 输入有效/就绪握手
- 输出结果有效
- 累加清零
- 流水线控制

## 6. 推荐的开发顺序

### 第一阶段：先做数值参考模型

先写软件 golden model，不要一开始直接写 RTL。

建议先做：
- E4M3 解码
- E8M0 scale 解释
- 单个 MX block dot-product
- FP32 参考累加

输出：
- Python 参考模型
- 随机向量测试脚本

### 第二阶段：做单个 LLMT

先把一个单元做对。

目标：
- 单 block 输入输出正确
- 和 golden model 对齐
- 波形可解释

### 第三阶段：扩成 16 路阵列

目标：
- 广播和多路权重调度正确
- 输出顺序正确
- 吞吐达标

### 第四阶段：补大规模验证

目标：
- 4096x4096
- 边界值覆盖
- 误差统计

### 第五阶段：综合与优化

目标：
- 初版综合
- 时序瓶颈定位
- 面积热点定位
- 功耗热点定位

---

## 7. 验证计划建议

建议按四层验证。

### 7.1 格式级验证

检查：
- E4M3 正常值
- E4M3 subnormal
- 最大值/最小值
- 符号位处理
- E8M0 scale 解释

### 7.2 算子级验证

检查：
- 单个 block dot-product
- 32 项规约结果
- FP32 累加正确性
- round-to-even 正确性

### 7.3 阵列级验证

检查：
- 广播通路
- 16 路权重并行
- 多拍流水结果对齐

### 7.4 系统级验证

检查：
- 4096x4096 矩阵乘
- 随机输入
- 边界输入
- 连续负载

---

## 8. 精度测试建议

题目要求比较最大相对误差，因此至少报告：

- 最大相对误差

建议额外补充：
- 平均相对误差
- P95/P99 相对误差
- worst-case 输入样本

建议至少区分下面几类测试集：
- 均匀随机
- 接近 0 的小数值
- 接近最大值的数值
- 混合正负
- 含大量 subnormal

## 10. 初赛高分关键点

想拿高分，重点不是只把代码写完，而是下面这些：

- 赛题理解准确，术语使用一致
- 结构选择有明确理由
- 验证覆盖足够全面
- 误差分析不是只给一个数字
- 面积和功耗分析有方法论

## 11. 决赛提前预埋的优化方向

初赛设计时就建议给这些方向留接口：

- 可配置中间精度
- 可配置流水级数
- scale 处理位置可替换
- 规约树结构可替换
- 支持更多 element 精度
- 支持稀疏或零跳过

## 12. 最后给团队的执行建议

如果团队人数是 3 到 5 人，推荐这样分工：

- 1 人：数值模型与测试平台
- 1 人：E4M3/E8M0/LLMT RTL
- 1 人：阵列顶层与控制
- 1 人：综合、功耗、脚本
- 1 人：报告整合与实验分析

如果只有 3 人，优先保证：
- golden model 正确
- 单 LLMT 正确
- 16 路阵列跑通
- 综合结果可信

不要一开始就追求“最优”，先做出一版可验证、可综合、可解释的架构。
